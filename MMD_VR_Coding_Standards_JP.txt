# MMD VRふれあいアプリ コーディング規約

## 1. 目的

本規約は、MMD VRふれあいアプリを長期的に開発・保守・拡張するためのコーディングおよび設計上の基本方針を定める。

本プロジェクトでは、現在の要件・技術選定を絶対的な前提としない。

要件定義書は現時点での方針を示すものであり、開発を進める中で以下のような変更が発生することを想定する。

* MMDモデルの取り込み方式の変更
* 外部ライブラリ・アセットの変更
* VR/XR SDKの変更
* 物理演算方式の変更
* エディタ時インポートから実行時インポートへの拡張
* MMD以外のモデルフォーマットへの対応
* UI・操作方式の変更
* パフォーマンス要件の変更
* フェーズ2以降の機能追加

そのため、本プロジェクトでは、

> **「現在動くコード」よりも「将来変更できるコード」を優先する。**

ことを基本方針とする。

---

# 2. 基本原則

## 2.1 変更を前提として設計する

実装時には、

> 「このコードは将来変更されるか？」

を常に考える。

特に以下は変更される可能性が高いものとして扱う。

* 外部ライブラリ
* SDK
* モデルローダー
* 物理演算システム
* XR入力
* モデルフォーマット
* データ保存形式
* UI
* ゲームルール
* パフォーマンス最適化方式

変更される可能性が高いものを、アプリケーションの中心ロジックへ直接依存させない。

---

## 2.2 「変更」より「拡張」を優先する

既存コードを大きく書き換えるのではなく、可能な限り既存コードを利用したまま新しい仕様へ対応できる設計を目指す。

悪い例：

```csharp
if (modelType == ModelType.Mmd)
{
    // MMD専用処理
}
else if (modelType == ModelType.Vrm)
{
    // VRM専用処理
}
```

モデル形式が増えるたびに既存クラスを修正する必要がある。

良い例：

```csharp
public interface IModelLoader
{
    bool CanLoad(ModelSource source);
    ModelData Load(ModelSource source);
}
```

新しい形式は `IModelLoader` の実装を追加することで対応する。

```text
PMXLoader
VRMLoader
GltfLoader
```

既存のモデル管理システムを変更せずに拡張できる構造を優先する。

---

# 3. 要件定義と実装を分離する

要件定義書に記載されている技術を、必要以上にコードへ直接埋め込まない。

現在の要件ではMMDモデルの取り込みにMMD for Unity、物理演算にMagica Cloth 2などを採用しているが、これらは将来変更される可能性がある。

そのため、

```text
ゲームロジック
    ↓
抽象化されたインターフェース
    ↓
外部ライブラリ
```

という依存関係を基本とする。

可能な限り、

```text
ゲームロジック
    ↓
MMD for Unity
```

のような直接依存を避ける。

---

# 4. 外部ライブラリへの依存

## 4.1 外部ライブラリの型を内部へ持ち込まない

外部ライブラリの型をゲーム全体のデータ構造として使用しない。

悪い例：

```csharp
public void ApplyModel(MmdForUnityModel model)
{
}
```

これではMMD for Unityを変更した際に、多数のクラスへ変更が波及する。

可能な限り、

```csharp
public void ApplyModel(ModelData model)
{
}
```

のように、自プロジェクトで定義した型を使用する。

---

## 4.2 アダプターを使用する

外部ライブラリ固有のAPIを使用する場合は、専用のAdapter / Wrapperを用意する。

```text
Game
 └─ Model System
      └─ IModelLoader
           └─ MmdForUnityModelLoader
                └─ MMD for Unity
```

外部ライブラリを変更する場合は、原則としてAdapter層を修正する。

---

# 5. 責務を分離する

1クラス1責務を基本とする。

特にUnityの `MonoBehaviour` に処理を集中させない。

以下のようなクラスは避ける。

```text
PlayerController
 ├─ 入力
 ├─ 移動
 ├─ モデル操作
 ├─ UI
 ├─ サウンド
 ├─ セーブ
 └─ 外部SDK処理
```

代わりに責務を分離する。

```text
PlayerInput
PlayerMovement
ModelInteraction
PlayerUI
SaveSystem
XRInputAdapter
```

`MonoBehaviour` はUnityとの接続部分として利用し、ゲームロジックを過剰に持たせない。

---

# 6. MonoBehaviourを神クラスにしない

Unityでは `MonoBehaviour` が便利であるため、何でもMonoBehaviourに実装しない。

特に以下の処理は可能な限り分離する。

* 計算処理
* データ管理
* ルール
* 変換処理
* 判定処理
* 状態管理
* 外部ライブラリとの変換

MonoBehaviourは、

> Unityオブジェクトとロジックを接続する役割

を基本とする。

---

# 7. 依存方向を意識する

依存関係は一方向にする。

基本的には、

```text
Presentation / Unity
        ↓
Application
        ↓
Domain
```

のように、上位の具体的な処理から下位の抽象的な処理へ依存させる。

特に、ゲームルールやデータモデルがUnity固有の実装へ依存しない構造を可能な範囲で目指す。

ただし、Unityプロジェクトである以上、すべてを完全にUnity非依存にする必要はない。

重要なのは、

> **Unityや外部SDKを変更したとき、ゲームの中心ロジックまで大量に変更しなくて済むこと**

である。

---

# 8. インターフェースの使用

インターフェースは「将来実装を変更する可能性がある箇所」に使用する。

特に以下はインターフェース化を検討する。

* Model Loader
* Input
* Save/Load
* Model Repository
* Physics Controller
* Animation Controller
* 外部SDKとの接続
* ファイルアクセス
* 時間取得
* ランダム値生成
* 通信

ただし、

> 「とりあえず全部interfaceにする」

ことは禁止する。

インターフェースは、

> **実装を差し替える理由が存在する場合**

に使用する。

---

# 9. 抽象化のタイミング

最初から過剰な抽象化を行わない。

以下の順番を基本とする。

```text
具体的な実装
↓
責務を整理
↓
変更点を特定
↓
必要な箇所だけ抽象化
```

将来変更される可能性があるからといって、まだ存在しない機能のために大量のインターフェースやFactoryを作らない。

「将来拡張できる構造」と「将来のための過剰設計」は区別する。

---

# 10. データと処理を分離する

設定値・ゲームデータ・状態・処理を可能な限り分離する。

例えば、

```text
ModelData
ModelRuntime
ModelController
```

のように、

* データ
* 実行時状態
* 制御処理

を区別する。

UnityではScriptableObjectをデータ管理に利用することを検討する。

ただし、ScriptableObjectを「何でも入れる共有グローバルデータ置き場」として使用しない。

---

# 11. SerializeFieldの使用

Unity Inspectorから設定する必要があるprivateフィールドには、

```csharp
[SerializeField]
private SomeType _someValue;
```

を使用する。

基本的に、Inspector設定のためだけにpublicフィールドを公開しない。

```csharp
public SomeType SomeValue;
```

より、

```csharp
[SerializeField]
private SomeType _someValue;
```

を優先する。

外部から読み取りが必要な場合は、必要に応じてプロパティやメソッドを提供する。

---

# 12. public APIを最小限にする

クラスの内部状態を外部へ公開しすぎない。

原則として、

```text
private
↓
protected
↓
internal
↓
public
```

の順で、必要最小限のアクセス範囲を選択する。

publicにすることは、

> 「このクラスが外部へ提供する正式なAPIを増やす」

ことを意味する。

そのため、安易にpublicへ変更しない。

---

# 13. 状態変更は明示的にする

外部から直接状態を書き換えられる設計を避ける。

悪い例：

```csharp
public bool IsGrabbed;
```

良い例：

```csharp
public bool IsGrabbed { get; private set; }

public void Grab()
{
    IsGrabbed = true;
}

public void Release()
{
    IsGrabbed = false;
}
```

状態変更にルールが存在する場合は、そのルールを変更操作へ集約する。

---

# 14. マジックナンバーを避ける

意味のある数値を直接コードへ書かない。

悪い例：

```csharp
if (distance > 0.15f)
{
}
```

良い例：

```csharp
private const float INTERACTION_DISTANCE = 0.15f;
```

ただし、意味のない定数を大量に作らない。

設定値として変更する可能性が高いものは、ScriptableObject等の設定データへ切り出すことを検討する。

---

# 15. 状態をenumだけで管理しすぎない

単純な状態管理ではenumを使用してよい。

ただし、

```csharp
if (state == State.A)
{
}
else if (state == State.B)
{
}
else if (state == State.C)
{
}
```

のような条件分岐が増えた場合は、State Pattern等の設計への変更を検討する。

状態追加のたびに既存コードを大量に変更する構造になった場合は、設計を見直す。

---

# 16. 条件分岐の増殖を防ぐ

以下のようなコードが増えた場合は設計を見直す。

```csharp
if (type == Type.A)
{
}
else if (type == Type.B)
{
}
else if (type == Type.C)
{
}
else if (type == Type.D)
{
}
```

特に、

> 新しい種類を追加するたびに既存クラスを変更する

構造は可能な限り避ける。

Strategy、Factory、Polymorphism、Registry等の利用を検討する。

ただし、単純な分岐まで無理にデザインパターンへ置き換えない。

---

# 17. Unityイベントへの依存を局所化する

`Update`、`FixedUpdate`、`OnCollisionEnter`等のUnityイベントは必要なクラスだけで使用する。

特にゲームロジックを大量の `Update()` に分散させない。

可能であれば、

```text
Unity Event
    ↓
Controller
    ↓
Application Logic
```

という構造にする。

---

# 18. Updateを増やしすぎない

常時更新が必要でない処理を `Update()` に置かない。

以下のような処理を優先する。

* イベント駆動
* 必要なタイミングでのメソッド呼び出し
* Coroutine
* Unityの物理イベント
* Input Systemのイベント
* 必要な場合のみUpdate

Quest 3では最低72fps、可能であれば90fpsを目標としているため、毎フレーム処理の増加は特に注意する。

---

# 19. パフォーマンス最適化と設計を両立する

最適化を理由に設計を無秩序に崩さない。

基本方針は、

```text
測定
↓
ボトルネック特定
↓
必要箇所のみ最適化
↓
設計への影響を確認
```

とする。

特にVRではフレームレートが重要だが、

> 「速そうだから」

という理由だけで責務分離や抽象化を破壊しない。

最適化した場合は、なぜその設計にしたのかコメント・ドキュメントへ残す。

---

# 20. モデルシステムは将来の形式追加を考慮する

現在はMMD/PMXを中心に扱うが、将来的にはVRM/glTF等への対応が想定されている。

そのため、MMD固有の概念をアプリケーション全体へ直接露出させない。

例えば、

```text
PMX
 ↓
MMD Loader
 ↓
ModelData
 ↓
Model System
```

という境界を設ける。

将来、

```text
VRM
 ↓
VRM Loader
 ↓
ModelData
```

を追加できる構造を目指す。

---

# 21. インポートシステムの設計

現在のフェーズ1ではエディタ時インポートを前提とする。

ただし、フェーズ2では実行時モデルインポートが予定されているため、エディタ専用APIをゲームロジック全体へ直接持ち込まない。

```text
Editor Importer
Runtime Importer
       ↓
共通ModelData
       ↓
Model System
```

のように、可能な範囲でインポート処理とモデル利用処理を分離する。

フェーズ1で完全なRuntime Import対応を実装する必要はない。

---

# 22. 物理演算システムへの依存を局所化する

現在はMagica Cloth 2を利用する方針だが、物理演算ライブラリは将来変更される可能性がある。

そのため、ゲーム側からMagica Cloth 2固有APIを直接操作する箇所を必要最小限にする。

```text
Interaction
    ↓
Physics Abstraction
    ↓
Magica Cloth 2
```

のような境界を検討する。

「Magica Cloth 2だからこうする」という処理と、

「揺れものをこう動かしたい」というゲーム上の要求を分離する。

---

# 23. XR入力を直接ゲームロジックへ渡さない

ハンドトラッキングやコントローラーなどの入力方式は将来変更される可能性がある。

ゲームロジックでは、

```text
「手がこの位置にある」
「この対象を掴んでいる」
```

などの意味のある情報を扱い、

```text
Meta XR SDKの具体的なAPI
```

を直接扱う範囲を限定する。

---

# 24. 命名

命名・フォーマットについては `.editorconfig` を正とする。

本規約では以下を特に重視する。

* クラス・メソッド・プロパティ：PascalCase
* インターフェース：IPascalCase
* privateフィールド：`_camelCase`
* ローカル変数・引数：camelCase
* 定数：UPPER_SNAKE_CASE

これらの詳細な形式は `.editorconfig` に従う。

---

# 25. コメント

コメントは「何をしているか」ではなく、

> **なぜこの実装になっているのか**

を説明するために使用する。

悪い例：

```csharp
// カウンターを1増やす
_count++;
```

良い例：

```csharp
// Quest上での入力遅延を抑えるため、ここではFixedUpdateではなくUpdateで処理する。
_count++;
```

特に以下は理由を残す。

* 一般的でない実装
* パフォーマンス最適化
* 外部ライブラリの仕様による制約
* SDKのバグ回避
* 将来変更予定の暫定実装
* 意図的に設計を妥協した箇所

---

# 26. TODOコメント

TODOは単なる「後でやること」のメモとして乱用しない。

悪い例：

```csharp
// TODO: あとで直す
```

良い例：

```csharp
// TODO: Runtime Import実装時にImporterの責務を再整理する。
// 現在はフェーズ1のEditor Import専用として実装している。
```

可能であればIssueや設計ドキュメントと紐付ける。

---

# 27. 例外処理

例外を握り潰さない。

悪い例：

```csharp
try
{
    Load();
}
catch
{
}
```

エラーを無視する場合でも、無視する理由を明確にする。

また、例外を使うべきではない通常の分岐に例外を利用しない。

---

# 28. Nullを適切に扱う

nullになり得るものと、絶対にnullにならないものを設計上区別する。

Unity Inspectorから設定される参照については、

```csharp
[SerializeField]
private ModelController _modelController;
```

のようにし、必要に応じて初期化時に検証する。

重要な依存関係が未設定の場合は、早期に明確なエラーを出す。

---

# 29. 依存関係の生成場所を集約する

依存オブジェクトを各クラスが勝手に生成しない。

悪い例：

```csharp
private readonly ModelLoader _loader = new ModelLoader();
```

必要に応じてDIやFactory等を使用し、依存関係の構築場所を明確にする。

ただし、現在の技術スタックは確定前であるため、特定のDIフレームワークの採用を本規約で固定しない。

---

# 30. 「newしやすい設計」を意識する

ロジッククラスは可能な限りUnityシーンに依存しない形で設計する。

例えば、

```csharp
public class ModelValidator
{
    public ValidationResult Validate(ModelData model)
    {
        // ...
    }
}
```

のような純粋なロジックは、UnityのGameObjectがなくてもテストできる構造を優先する。

---

# 31. テスト可能性を設計段階から考える

実装時には、

> 「このコードをどうテストするか？」

を考える。

特に以下のロジックはUnityのSceneやGameObjectから分離できる場合、分離する。

* 数値計算
* 判定
* 状態遷移
* モデルデータ変換
* 設定値の検証
* インポートデータの検証
* 操作ルール

---

# 32. クラスを巨大化させない

以下の兆候が見られた場合はクラス分割を検討する。

* フィールドが大量に増えた
* publicメソッドが大量に増えた
* `if` / `switch` が増え続ける
* 複数の異なる責務を持っている
* 変更理由が複数存在する
* 一部の処理だけ頻繁に変更される
* テストが困難
* クラス名に「Manager」が付いているだけで責務が説明できない

特に `XXXManager` は「何を管理するクラスなのか」を明確にする。

---

# 33. Managerクラスの乱立を避ける

以下のようなクラスを安易に作らない。

```text
GameManager
ModelManager
UIManager
DataManager
SystemManager
```

「Manager」という名前だけでは責務が不明確である。

代わりに、

```text
ModelLoader
ModelRepository
ModelSpawner
ModelController
ModelSelectionPresenter
```

など、何をするクラスなのか分かる名前を優先する。

---

# 34. Singletonの使用

Singletonは原則として乱用しない。

特に、

```csharp
SomeManager.Instance
```

をどこからでも呼べる状態を安易に作らない。

Singletonを使用する場合は、

* 本当に唯一の存在である必要がある
* グローバルアクセスが必要である
* ライフサイクルを明確に管理できる

などの理由を持つ。

---

# 35. 静的状態を最小化する

static変数によるグローバル状態を可能な限り避ける。

理由：

* テストが難しくなる
* 初期化順序に依存する
* Scene切り替えで状態が残る
* 依存関係が見えなくなる

特にゲームの状態をstaticで保持しない。

---

# 36. 設計パターンは目的から選択する

デザインパターンを使うこと自体を目的にしない。

例えば、

* 実装を切り替えたい → Strategy
* オブジェクト生成を隠したい → Factory
* 外部APIを内部仕様へ変換したい → Adapter
* 状態による処理を分離したい → State
* イベント通知を分離したい → Observer

というように、

> **解決したい設計上の問題からパターンを選ぶ。**

パターン名を先に決めてから問題を当てはめない。

---

# 37. 「今は1種類だから」を理由に密結合しない

現在1種類しか存在しない場合でも、将来追加される可能性が高いものは境界を意識する。

ただし、最初からすべてを抽象化する必要はない。

重要なのは、

> **将来拡張する際に、既存コードのどこを変更すればよいかが明確であること**

である。

---

# 38. 技術選定が未確定な部分を固定しない

要件定義書には未決定事項が存在する。

例えば、

* MMD for Unityの保守状況
* Blender経由への切り替え
* Application SpaceWarp
* OpenXR StickControl
* Scene機能の利用方法

などである。

これらについて、現在の候補技術を絶対条件としてコードへ組み込まない。

「仮採用」「検証中」「将来変更予定」の技術には、変更境界を設ける。

---

# 39. 暫定実装を正式設計と混同しない

検証目的のコードと、正式なゲームコードを区別する。

プロトタイプでは、

```text
最速で検証できる実装
```

を選択してよい。

ただし、検証成功後に正式実装へ移行する際には、

```text
検証コード
↓
責務整理
↓
依存関係整理
↓
正式実装
```

という段階を設ける。

---

# 40. 技術検証コードを本番コードへ直接流用しない

外部SDKやライブラリの動作確認用コードは、正式なアーキテクチャとは分離する。

例えば、

```text
Tests/
Prototype/
Sandbox/
```

などに配置し、正式なシステムと区別する。

検証コードがそのまま本番システムの依存関係になることを避ける。

---

# 41. 「変更の影響範囲」を小さくする

実装時には、

> 「この仕様が変更された場合、何個のクラスを変更する必要があるか？」

を意識する。

理想は、

```text
仕様変更
↓
1つまたは少数の実装変更
↓
既存システムはそのまま
```

である。

多数のクラスを同時に変更しなければならない場合、責務分離や抽象化を再検討する。

---

# 42. 変更理由の異なるコードを分離する

同じクラスに、

```text
UI変更で修正するコード
物理変更で修正するコード
モデル変更で修正するコード
入力変更で修正するコード
```

を混在させない。

「何が変わったら、このクラスを修正するのか」を考え、その変更理由が複数ある場合は分離を検討する。

---

# 43. データ形式変更への耐性を持たせる

将来の保存形式やモデルデータ形式の変更を考慮し、内部ロジックと保存形式を直接結びつけない。

```text
保存データ
 ↓
Deserializer
 ↓
Internal Data
 ↓
Game Logic
```

のような変換層を設ける。

---

# 44. APIは変更されるものとして扱う

外部SDKだけでなく、自分たちのクラスのAPIも将来変更される。

そのため、

```csharp
public
```

を増やすほど変更コストが上がることを理解する。

公開APIは最小限にし、内部実装を自由に変更できる範囲を確保する。

---

# 45. リファクタリングを負債ではなく開発工程として扱う

長期プロジェクトでは、最初から完璧な設計を作ることは現実的ではない。

そのため、

```text
実装
↓
検証
↓
問題発見
↓
リファクタリング
↓
拡張
```

のサイクルを前提とする。

「一度動いたから触らない」ではなく、

> **変更によって設計上の問題が見つかったら、その時点で改善する。**

---

# 46. コードレビュー時の確認事項

コードレビューでは、単純なコーディングスタイルだけでなく以下を確認する。

### 責務

* このクラスの責務は明確か
* 責務が増えすぎていないか
* Unity APIに依存しすぎていないか

### 依存関係

* 外部ライブラリへ直接依存していないか
* 依存方向が適切か
* 不必要なSingleton/static依存がないか

### 拡張性

* 新しい種類を追加するとき既存コードを大量に変更しないか
* 条件分岐が増殖しないか
* 新しいモデル形式に対応しやすいか

### 変更容易性

* 仕様変更時の影響範囲は小さいか
* 外部SDKを変更できるか
* データ形式を変更できるか

### テスト

* ロジックを単体で検証できるか
* Unity Sceneに依存しすぎていないか

### パフォーマンス

* 不必要な毎フレーム処理がないか
* Quest 3の性能制約を考慮しているか
* 最適化によって設計が不必要に複雑化していないか

---

# 47. 設計判断の記録

重要な設計判断はコードだけに残さず、ドキュメントにも記録する。

特に以下は記録する。

* なぜこの技術を選んだか
* なぜ別の技術を採用しなかったか
* なぜこの抽象化を作ったか
* なぜこの設計を妥協したか
* 将来変更する予定があるか
* 既知の制約は何か

技術選定が変更された場合、コードだけを変更して過去の設計意図を失わないようにする。

---

# 48. 要件定義書を絶対視しない

要件定義書は「現在の理解」を表すものであり、長期プロジェクトでは変更される。

したがって、

```text
要件定義
↓
設計
↓
実装
```

を一方向の絶対的な流れとして扱わない。

実装・検証によって問題が発見された場合は、

```text
実装
↓
問題発見
↓
設計変更
↓
要件の再確認
```

を行う。

ただし、コード側の都合だけで要件を勝手に変更しない。

---

# 49. 「設計を守ること」より「変更に耐えられること」を優先する

設計原則を守ること自体を目的にしない。

例えば、

* interfaceを増やしすぎる
* Factoryを多重にする
* 抽象クラスを大量に作る
* DIを過剰に導入する

などによって、かえって変更が難しくなる場合がある。

重要なのは、

> **変更される可能性が高い部分を変更しやすくすること**

である。

変更されない部分まで過剰に抽象化しない。

---

# 50. 最終原則

本プロジェクトでは、以下を最重要ルールとする。

1. **現在の仕様だけでなく、将来の変更を考えて実装する。**
2. **変更される可能性が高いものを、中心ロジックへ直接依存させない。**
3. **外部ライブラリ・SDKへの依存範囲を限定する。**
4. **1クラス1責務を基本とする。**
5. **public APIを必要最小限にする。**
6. **変更理由の異なるコードを分離する。**
7. **新機能追加時に既存コードを大量変更しなくて済む構造を優先する。**
8. **ただし、将来のための過剰設計は行わない。**
9. **技術選定が未確定な部分は、変更可能な境界を設ける。**
10. **パフォーマンス最適化は測定結果に基づいて行う。**
11. **検証用コードと正式なゲームコードを区別する。**
12. **設計上の判断理由を記録する。**
13. **実装によって問題が判明した場合は、設計を見直すことを恐れない。**
14. **「動くコード」ではなく「理解・変更・拡張できるコード」を目指す。**

---

## 付録：実装前のチェック

新しいクラスやシステムを実装する前に、以下を確認する。

* [ ] このクラスの責務を一文で説明できるか
* [ ] このクラスが変更される理由は何か
* [ ] Unity固有処理とロジックを分離できないか
* [ ] 外部ライブラリへの依存を局所化できないか
* [ ] 将来実装を差し替える可能性があるか
* [ ] 新しい種類を追加したとき既存コードを大量変更しないか
* [ ] public APIは本当に必要か
* [ ] static / Singletonにする必要があるか
* [ ] テストしやすい構造になっているか
* [ ] 毎フレーム処理は本当に必要か
* [ ] 「将来のため」という理由だけで過剰設計していないか

## 付録：変更時のチェック

仕様変更が発生した場合は、実装前に以下を確認する。

* [ ] 既存コードを直接変更する必要があるか
* [ ] 拡張によって対応できないか
* [ ] 変更の影響範囲はどこまでか
* [ ] 外部ライブラリとの境界を越えていないか
* [ ] 複数クラスに同じ変更が必要になっていないか
* [ ] 今回の変更によって新しい抽象化が必要になったか
* [ ] 要件定義書・設計資料との整合性を確認したか
* [ ] 将来の変更可能性を狭めていないか

# 51. 制御構文の記述規則

if文やfor文などの制御構文では、処理が1行だけの場合でも必ず波括弧（`{}`）を記述する。
省略した構文は後から処理を追加する際のバグの原因になりやすいため、本プロジェクトでは禁止とする。

悪い例：
```csharp
if (isReady) return;

if (count > 0)
    count--;
```

良い例：
```csharp
if (isReady)
{
    return;
}

if (count > 0)
{
    count--;
}
```
